## Предлагаемая минимальная модель

Решения интеграционного координатора после исследования: исходный каталог содержит 20 номеров, №6 — статистика; seed всей taxonomy и явно помеченных synthetic задач допустим. Пробник показывает raw sum/max. Default timezone `Europe/Moscow`; streak засчитывает день хотя бы с одной успешно проверенной задачей (`graded`, даже с неверным ответом), без quiz progress; solved означает полный балл. Учебные минуты учитываются отдельным ограниченным heartbeat. Unsupported grader и неподтверждённая математика явно обозначаются.

Одна существующая PostgreSQL 17 для данных, сессий и очереди заданий; private S3-compatible storage для изображений. Не нужны отдельная document DB, Redis или broker для первого интегрированного контура. Ниже логические таблицы, окончательные имена и номера миграций согласуются в общей спецификации. UUID генерирует сервер; время — `timestamptz`, учебный день — `date` в сохранённой timezone пользователя.

| Сущность | Данные и инвариант |
|---|---|
| `users` | Сохранить существующие ID/auth/hash/created_at; API `registeredAt` = `created_at`, не вторая дата. Добавить FK `preparation_level_id`, `plan_id`, nullable `avatar_object_id`, `daily_goal_minutes`, `timezone`. Hash остаётся nullable для external login; hash и служебные auth-поля не выходят в profile DTO. |
| `preparation_levels`, `plans` | Стабильные коды справочников; seed известных UI значений, включая `free`/`pro`. Уровень существующего пользователя unknown/null до onboarding, не придуманная оценка. Default plan free. Изменение тарифа доступно только серверному административному/платёжному процессу. |
| `user_activity_days` | PK `(user_id, local_date)`, `active_seconds`, `qualified_at`, snapshot `goal_minutes`, timezone; обновление идемпотентно по событиям активности. `streak_days` — вычисляемая проекция последовательных qualified дней, API также отдаёт реальный массив дней недели. Один изменяемый счётчик streak не является источником истины. |
| `subjects`, `topics` | Topic принадлежит subject; ключи справочников стабильны. `task_version_topics(version_id, topic_id)` — M:N, не CSV/массив пользовательских строк. При публикации проверяется совпадение предмета. |
| `exam_formats`, `exam_positions` | Versioned формат, subject/year и число позиций; позиции: порядковое место, часть, отображаемый номер, официальный номер при наличии. `UNIQUE(format_id, position)` и `(format_id, display_number)`. Project grader number хранится отдельным explicit mapping, не выводится арифметически из номера в UI. |
| `tasks`, `task_versions` | `tasks` — стабильная идентичность, current published version и archive marker. Version: UUID, task FK, revision, exam_position FK (отсюда предмет/часть/номер), source year, difficulty, answer form, max points, condition, reference answer, reference solution, schema version, content hash, author/time. `UNIQUE(task_id, revision)`; content immutable. Изменение любого значимого поля создаёт новую версию. |
| `task_version_answers`, `task_version_assets` | Accepted short answers и порядок/роль изображений связаны с конкретной version. Rich-text condition/solution допускают schema-validated JSONB blocks; отношения, фильтры и баллы — обычные колонки. Опциональное изображение — FK объекта, не произвольный URL. Опубликованная задача требует заполненных condition/answer/reference solution; неполные mock seeds не публикуются. |
| `exam_templates`, `exam_template_versions`, `exam_template_items` | Стабильный template и immutable состав его revision. Item ссылается на `task_version_id` и position. Публикация целевого BotAI-формата разрешена только для **20** уникальных позиций с подходящими задачами; простой `CHECK` на одной строке не проверит число children. Нужны атомарная publish-транзакция с блокировкой parent и constraint trigger на published состав. |
| `attempts`, `attempt_items` | Attempt принадлежит user, тип exam/practice/favourites, nullable template_version FK, статус/время/cursor. При старте в одной транзакции создаются все items с immutable `(ordinal, task_version_id)` и rubric/grader version. Это персональный snapshot: редактура каталога не меняет состав, условие, ответы или максимум старой попытки. Содержимое не надо дублировать blob, если referenced version физически неизменяема и не удаляется. |
| `practice_selections` | PK `(attempt_id, exam_position_id)`, выбранное количество `>0`; отдельные difficulty/topic filters при необходимости. Сервер материализует items один раз, проверяет доступный bank и возвращает недобор как явную ошибку; не дополняет неизвестными/чужими задачами. Повторный старт с тем же idempotency key возвращает ту же попытку. |
| `attempt_item_drafts` | Answer, revision, updated_at и private drawing ref; draft изменяем, на grading копируется immutable input revision. Optimistic concurrency предотвращает затирание второй вкладкой. Новый attempt начинает ответы пустыми; рисунок незавершённой canonical task можно предложить как восстановление, не как проверенный ответ. |
| `user_favourites` | PK `(user_id, task_id)`, added_at. Привязка к canonical task, не к version/attempt и не `examId:taskId`; listing возвращает TaskSummary из общего банка, иначе избранное из пробника потеряется. Повторные add/remove идемпотентны. |
| `user_task_results` | PK `(user_id, task_id)`, first/last solved_at, latest submission FK и current summary; восстанавливаемая проекция валидных результатов. История — отдельные submission/result записи, никогда не перезаписывается новой оценкой. Partial score не равен solved; proposed solved = полный балл. |

`reference_answer`/solution закрыты в student task DTO до предусмотренного раскрытия. AI получает доверенную server-side task version, а не ответ/баллы/идентификатор, присланные браузером. User/task/item владение проверяется запросом с user_id; UUID сам по себе права не даёт. FK на исторические версии — RESTRICT, пользовательские отношения не удаляются каскадом вместе с задачей.

## Предлагаемый контур проверок и аудита

- `grading_submissions`: user FK, attempt_item FK (nullable у отклонённого неизвестного item), server request ID, submitted target ID как ограниченные untrusted metadata, input revision/hash, idempotency key, status, created/started/finished, error/rejection codes. Owner берётся из сессии. `UNIQUE(user_id, idempotency_key)`; тот же ключ с другим payload → conflict, с тем же → прежний результат.
- Сначала лёгкий `POST` intent с durable row, **потом** upload и finalize. Ошибочный target, limit/format validation reject записывается и коммитится отдельно от проваленной domain-транзакции. Multipart/413, оборванная загрузка и локальное прекращение после intent оставляют след; expiry завершает незаконченный intent с причиной. Клиентская отмена до любого сетевого intent принципиально серверу неизвестна.
- Состояния: `CREATED → UPLOADING → QUEUED → RUNNING → GRADED | REJECTED | FAILED | CANCELLED | EXPIRED`. `REJECTED` различает input validation и model rejection; failed/timeouts/cancelled не создают score=0. Прежняя ошибка сохраняется при явном retry новым submission с `retry_of_id`.
- `submission_events`: append-only `(submission_id, sequence)` unique, тип/время/actor/request ID и ограниченная schema-validated metadata. Журналировать все переходы, image validation, отказ, отмену и поздний ответ worker; runtime роль не UPDATE/DELETE. Raw OCR, cookies, passwords, signed URL и полный provider body не попадают в общий журнал.
- `grading_runs`: submission FK, run UUID, fencing token/lease, pipeline/prompt/rubric version, provider/model identifier, start/end, normalized outcome, provider request ID; повторная доставка очереди не означает разрешение повторно оплачивать вызов. После неопределённого provider timeout фиксируется FAILED/unknown outcome и нужен явный retry, не бесконечная автопроверка.
- `grading_results`: один принятый result на submission, `is_graded`, nullable score, snapshot max_points, exact validated response text/hash + schema version и структурированный projection. CHECK: graded → score в `[0,max_points]`; иначе score NULL. Принятие сверяет authoritative task и image IDs; неверный score не clamp. JSONB сам не сохраняет точные исходные bytes — нужен text/bytes для exact artifact.
- `work_items`/outbox создаётся в той же транзакции, что QUEUED и event; worker коротко забирает lease через `FOR UPDATE SKIP LOCKED`, commit, затем вызывает AI **вне DB-транзакции**. Watchdog обрабатывает expired leases; accepted result, terminal event и обновление solved projection коммитятся атомарно. Это at-least-once доставка с идемпотентным применением, не обещание exactly-once provider call.
- Отмена — conditional transition по текущему статусу/fencing token. Поздний result после CANCELLED сохраняет факт позднего исхода в audit, но не меняет student score/progress. Закрытая вкладка не равна отмене server job. При недоступной БД запрос не считается принятым и AI не запускается; proxy/auth/CSRF отказы до intent фиксирует отдельный ограниченный security log.

## Файлы и админка

- `stored_objects`: UUID, owner, purpose, bucket/key, optional object version, server-calculated SHA-256, media type/bytes/dimensions, state, created/retention/deleted times; `UNIQUE(bucket,key)`. `submission_images` связывает submission/object и ordinal, unique на порядок; ownership/purpose проверяется до привязки. Photo не хранится BYTEA в users/submission.
- Минимальный upload проходит backend с потоковым лимитом, decode/re-encode и удалением EXIF; private S3 получает очищенный файл. Существующие лимиты AI: JPEG/PNG/WebP, 8 MiB/file, 20 MP, 8192 px, 1–4 solution photos; AI повторяет валидацию. Unsafe/oversized bytes не обязаны сохраняться ради аудита, сохраняются reason/size/type и image slot.
- S3/DB не имеют общей транзакции: сначала reserved metadata, затем upload в уникальный неизменяемый key, finalize проверяет объект и ставит READY; orphan/staging sweeper удаляет брошенные объекты. Deletion тоже двухфазный (`DELETE_PENDING` → удаление → tombstone), не скрывает ошибку storage. Key/filename задаёт сервер; object никогда не перезаписывается после принятия.
- Private bucket с блокировкой public access, scoped service credentials; private photos и avatars не смешиваются с публичными assets задач. UI получает временный GET только после owner/admin authorization; signed URL не хранится в БД/логах. AI получает проверенные bytes через backend/service boundary, не произвольный пользовательский URL.
- `admin_access_events`: actor, действие, target submission/object/user, timestamp, request ID, outcome; просмотр фото, выдача signed URL и изменение moderation state аудируются. Admin listing показывает metadata/status/score/error без автоподгрузки фото; detail — по отдельной авторизации. `ADMIN` уже есть в users, но текущая security config пока требует только authentication, admin endpoints ещё отсутствуют.
- Retention задаётся отдельно для images, OCR/result detail и минимального audit. Текущие 30 дней AI attack store — факт существующего режима, не согласованный общий срок. При удалении media остаётся tombstone, аудит не теряется; task assets удерживаются, пока нужны immutable versions. Backups и lifecycle должны следовать той же политике.

## Ограничения, индексы и миграция

- База ограничивает enum-like статусы/answer forms/difficulty, `daily_goal_minutes >0`, `max_points >0`, `0≤score≤max_points`, положительные counts/ordinals, FK и unique. Cross-row количество items, совпадение subject/format и целостность published версии проверяются publish-функцией/trigger; нельзя подменять их CHECK с чтением других таблиц.
- Индексы: attempts `(user_id, created_at DESC, id)`; items unique `(attempt_id, ordinal)`; submissions `(user_id,created_at DESC,id)`, `(attempt_item_id,created_at DESC)`, admin `(status,created_at,id)`; events unique `(submission_id,sequence)`; ready work partial `(available_at,id)`; favourites `(user_id,added_at DESC,task_id)`; results `(user_id,last_solved_at DESC)`; versions `(exam_position_id,difficulty,source_year,id)`; topics reverse `(topic_id,version_id)`; objects partial cleanup `(retention_until,id)` по соответствующим состояниям. FK child-side индексы добавлять по join/delete запросам; PostgreSQL не создаёт их автоматически.
- Перед реализацией согласовать общий baseline с email-ops: сохранить V1–V4 bytes/checksums, production schema history и auth API. Новые последовательные миграции начинаются **после V4**, без Flyway repair/baseline/drop и без редактирования применённых файлов. Проверить production checksum read-only перед deploy.
- Expand → backfill → validate: сначала справочники/новые таблицы и nullable profile FK; seed справочников; small-batch backfill free plan, явно выбранной timezone/goal; лишь затем NOT NULL где продукт действительно требует. Existing created_at/password hash/session/email_verified не преобразовывать. Новые FK к большим таблицам можно добавлять NOT VALID и валидировать отдельно.
- Перед изменениями сделать проверяемый backup и restore rehearsal; volume не удалять, `docker compose down -v` запрещён. Rollback приложения должен читать расширенную схему; data-preserving rollback не откатывает новые таблицы/историю. Browser mocks и тестовые AI IDs автоматически в production не импортировать; bank импортировать со stable source mapping и review gate.
- Проверки будущей реализации: upgrade V4 с существующим local/OAuth user и session; immutable task edit при открытой попытке; 20-slot publish; duplicate finalize/retry/cancel races; reject/timeout/storage failure сохранены без оценки; cross-user image/item access; worker crash; orphan cleanup и восстановление backup. Только mocks/offline, никаких paid calls.

## Unresolved перед реализацией

Нужны supported grader mapping для остальных номеров, правила смены timezone без удвоения streak, значения onboarding справочников/default goal, сроки хранения/удаления, конкретный private S3 endpoint и bucket. Front seed на 19 задач требует исправления по принятому каталогу на 20. Synthetic seeds не становятся математически проверенными автоматически. Часть unresolved можно задать временным продуктовым решением с явной пометкой.

Основания технических ограничений: [PostgreSQL constraints](https://www.postgresql.org/docs/17/ddl-constraints.html), [PostgreSQL SELECT/locking](https://www.postgresql.org/docs/17/sql-select.html), [S3 presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html), [S3 Block Public Access](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html). Private signed URL является временным bearer-доступом; его выдача требует проверки прав и короткого TTL.
