Browser URLs must remain server-owned, bounded and nosniff; no hotlinking or arbitrary Next image optimizer fetches. Do not introduce new infrastructure for this boundary.

An existing maintained equivalent is acceptable only with the same controls; for example, [CairoSVG documentation](https://cairosvg.org/documentation/) describes external-resource support and an unsafe mode, so using its default entry point is not by itself a no-network guarantee.

**Converter profile.** Validate UTF-8 XML before rendering; reject DTD/entity declarations, processing instructions and gzip/svgz. Start with source-observed path-based math: svg, g, defs, path, rect, line, polyline, polygon, circle, ellipse; allow local use/clipPath only where the observed sample needs them. Enforce namespace/attribute allowlists and finite geometry. Reject script, event attributes, foreignObject, animation, filters/masks, image, external stylesheets, CSS imports/URL values, arbitrary style declarations, external href/xlink:href and xml:base. Allow `href="#id"` only inside the same document with unique IDs, acyclic references, bounded depth and bounded expanded-node/path-command count; checking the raw node count alone misses exponential use expansion. Reject unsupported content rather than deleting visible pieces.

Path glyphs require no fonts. Text-bearing SVG needs a separately reviewed profile with a fixed trusted bundled font and deterministic metrics; it must never discover/load source-supplied fonts or arbitrary host files. Use a renderer API with external resource resolution disabled plus a restricted worker process: no network, no host credentials, no arbitrary host mounts, readonly input, private scratch output, non-root, one conversion at a time, 256 MiB memory, 5-second wall timeout. Existing one-shot container/process tooling is sufficient, no new service. A converter crash/timeout is a quarantined asset, not an import retry loop.

Proposed initial per-formula caps: 512 KiB source SVG, 10,000 XML nodes, depth 32, at most 50,000 expanded path commands/nodes, 4,096 pixels/side and 4 million output pixels. Do not discard meaningful colour, clipping or fraction strokes to fit this profile. Parse/normalize the resulting single-frame PNG independently, cap encoded output to 8 MiB, and retain original and transformed hashes plus converter/version/options. Renderer output for line art should stay lossless PNG; blindly reusing the existing JPEG-only ImageNormalizer can visibly damage small glyphs. **Ordering and layout.** Traverse the source DOM in document order and preserve every text/inline-formula run, paragraph break and figure anchor. Do not collect all text first then append formulas, replace formulas with alt text, or emit each small formula as a full-width figure. A minimal additive paragraph representation can contain ordered text, exact-LaTeX or formula-asset runs. Formula dimensions and baseline must be bounded numeric values derived from the source's measured/declared geometry, never arbitrary CSS. Figures remain separate image blocks. The frontend owner must validate the proposed representation against its renderer; it is not accepted merely by adding JSON fields. If exact accessible math text is absent, do not pretend a generic alt label is an equivalent mathematical transcription.

Replace the fixed four-image ceiling with separate budgets, initially up to 128 paragraphs/figure blocks, 1,024 inline runs, 256 formula assets and 16 figures across statement and reference content; cap total normalized asset bytes at 64 MiB and decoded pixels at 64 million per task. Count all assets, even duplicates, for layout complexity; deduplicate storage by content hash within the same access class. These are adjustable parser/resource budgets, not claims about how many formulas a valid task ought to contain. Exceeding them reports exact observed sizes/counts for review, never truncation or unexplained loss.
