## Зафиксированные требования пользователя

- Короткая основная инструкция направляет модель к файлам инструкций на сервере.
- Распознавание и анализ объединены: аналитик видит фото и может вернуться к спорному месту.
- Оценку выставляет отдельный вызов с новым контекстом, на основании критериев и результатов анализа.
- Вход каждой задачи содержит верный ответ; Wolfram и внешняя система решения не нужны. Верный ответ не заменяет проверку выкладок.
- Справочник типичных ошибок содержит только общие ситуации, оценки и обязательные математические условия; источники и примеры вынесены из текста для модели.
- Минимум файлов и повторов. Общие правила выносятся только при реальной общей ответственности.
- После сжатия контекста сохраняются основная инструкция и возможность продолжить с текущего этапа.

## Предлагаемая схема

`Вход → чтение фото + анализ ↔ повторный просмотр → зафиксированный отчёт → независимое выставление балла → проверки сервера → результат`.

**Аналитик:** читает инструкцию анализа и справочник, транскрибирует решение с привязкой к фото; проверяет каждое преобразование, ограничения, случаи и ответ. Отдельно фиксирует выполненные проверки, ошибки и неразрешённые сомнения. Не назначает балл. Классификация математического недостатка и недостатка оформления делается здесь, как требует AGENTS.md.

**Оценивающий:** новый контекст; получает условие, верный ответ, действующие критерии, проверенную транскрипцию, доказанные замечания и покрытие проверок. Не получает историю рассуждений аналитика или предполагаемый балл. Для каждого решения об оценке указывает критерий и факты. При недостаточных/противоречивых данных запрашивает уточнение аналитика; сам незаметно не меняет классификацию ошибки. Это независимость выбора балла, но не независимая повторная математическая проверка.

**Сервер:** выбирает пакет по схеме/номеру, задаёт этап, сохраняет результаты и проверяет переходы. Не позволяет завершить оценивание без обязательных данных. Числовые границы и допустимые баллы проверяются Python после ответа модели; модельные схемы и внешние ответы остаются разными.

## Чтение файлов и восстановление

Рекомендуемый вариант для обсуждения: модель вызывает `read_instruction(document_id)`. Сервер разрешает только документы выбранной задачи и общие правила. Произвольные пути, файлы другой работы и служебные секреты недоступны. Текст/фото ученика остаются данными и не могут выбирать инструкции.

В нынешнем `app/llm/types.py` нет сообщений инструментов, а вызовы пайплайна завершаются структурированным ответом. Буквальное чтение файлов потребует расширения общего LLM-слоя и поддержки инструментов у выбранного провайдера; не маскировать это одной фразой в промпте. Альтернатива — сервер читает Markdown и подставляет содержимое в очередной запрос.

Кандидат минимального пакета исполнения: общая `main.md`; для №16 — `criteria.md`, `pitfalls.md`, `analysis.md`, `grading.md`. Заметки обсуждения модель не читает. Файлы инструкций версионируются; проверка закрепляет конкретную версию всего пакета, включая индивидуальные критерии.

Контрольная точка хранится сервером: идентификатор работы, этап, версия инструкций, исходные фото, транскрипция, проверенные шаги, замечания, сомнения, следующий шаг и использованный бюджет. Сжатие истории не удаляет эти данные. Новый контекст получает основную инструкцию, контрольную точку и заново нужные файлы/изображения. Модель не должна «помнить сама», какие правила прочитала.

До реализации задать конечные лимиты просмотров, уточнений и общего бюджета; исчерпание лимита — явное незавершённое состояние, не выдуманный балл. Завершённый этап не повторять автоматически после сбоя без проверки сохранённого результата.

## Минимальный контракт данных — предложение

| Объект | Содержание |
| --- | --- |
| Вход | Схема нумерации, номер, условие, верный ответ, упорядоченные фото или текст решения; индивидуальные критерии и эталонное решение необязательны |
| Строка | ID, буквальная запись, фото/область, альтернативные чтения при сомнении; исправления распознавания отдельным журналом |
| Проверка | Шаг/условие, `verified / violated / unresolved / not_applicable`, свидетельство; обязательно ограничения, переходы, полнота случаев и ответ |
| Замечание | ID, правило справочника, место, наблюдаемый факт, объяснение, влияние на дальнейшее решение, статус распознавания; разделение математики/оформления |
| Передача оценщику | Полная проверенная транскрипция, проверки и замечания; ни балла, ни рекомендаций «снять столько-то» аналитика |
| Выход | Состояние, выбранный критерий и его версия, балл после проверки сервера, ссылки на факты, короткая обратная связь по-русски; точная форма балла обсуждается |

Одна ошибка и её следствия связываются, а не штрафуются многократно. Отсутствие найденных ошибок недостаточно для 2 баллов: требуется подтверждённая полнота проверки. Индивидуальные критерии имеют приоритет над общими; несовместимые с ними правила справочника не применяются.

## Интеграция и проверка будущей реализации

Переиспользовать общий LLM-клиент, ошибки `ServiceError`, `X-Request-ID`, учёт затрат, защиту debug, проверку результатов и загрузку шаблонов там, где подходят их контракты. Маршруты отвечают за транспорт; предметная логика №16 не проникает в общий LLM-слой. Числовые каталоги ресурсов выбираются явным реестром, без динамического исполнения пути из запроса.

Текущие `prompts/shared/_handwriting.md` разрешают исправлять некоторые символы по согласованности выкладок. Не переносить эту эвристику автоматически: новый вариант требует различать видимую ошибку ученика и ошибку чтения. Текущий режим анализа фото уже существует, но сам по себе не реализует инструменты повторного просмотра и сохранённое состояние.

Приёмочные сценарии: корректное решение без отдельного заголовка ОДЗ → 2; только допустимые граничные точки → 1; включён нуль знаменателя → 0; вычислительная ошибка при всех верных шагах → 1; правильный ответ при ошибочном методе → по критерию, возможен 0; эквивалентный нестандартный метод → без снижения; неразборчивость → пока вне обсуждаемой области; возобновление → те же фото, версия критериев и подтверждённые факты; №16/2026 не смешивается с №16/2027; инструкции на фото не исполняются.

Для предметной калибровки использовать примеры 15.1.1–15.6.2 из PDF с указанными оценками экспертов. Mock проверяет маршрутизацию, контракты и переходы, но не доказывает качество реальной модели. Промпты проверять через offline preview; живые вызовы — только по отдельному явному запросу пользователя. Во время текущего проектирования платные вызовы не нужны.
