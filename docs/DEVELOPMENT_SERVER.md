# Изолированный DEVELOP и шлюз

Состояние на 1 октября 2026. Основной сервис остаётся в `/srv/ege/app`.
Его содержимое, права файлов, `.env`, образ и конфигурация контейнера сохранены.
Новые каталоги без дополнительного уровня `ege/`:

| Назначение | Путь / доступ |
| --- | --- |
| Основной сервис | `/srv/ege/app`, прежний контейнер `ege-grading-api` |
| DEVELOP | `/srv/develop`, пользователь `botai-dev`, rootless Docker |
| Шлюз | `/srv/gateway`, отдельный пользователь `botai-gateway` |
| Диск DEVELOP | `/srv/botai-develop-storage.img`, 8 ГБ, ext4 |
| Общая публичная инструкция | https://api.botai-ege.ru/ |
| Личная инструкция разработчика | `/srv/develop/README.md`; локально `~/.config/botai/develop-access.md` |
| Приватный веб-доступ DEVELOP | `~/.config/botai/develop-web-access.md`, вне Git |

8 ГБ — выбранный при настройке предел дискового пространства для всего DEVELOP,
а не дополнительный оплачиваемый диск и не оперативная память. Файл-образ находится
на существующем диске сервера 50 ГБ; фактическое занятое место зависит от содержимого.
В предел входят домашняя папка разработчика, проект, Docker-образы, контейнеры,
данные и временные файлы. Лимит RAM задан отдельно: 1500 МиБ на пользовательскую
slice. Основной сервис и шлюз в эти два лимита не входят.

## Как работает доступ

Разработчик подключается собственным SSH-ключом. Его публичный ключ хранится в
root-owned `/etc/ssh/authorized_keys/botai-dev`. Нет sudo и доступа к системному
Docker. Собственный rootless Docker доступен через `/run/user/1000/docker.sock`.
Изменения загружаются в DEVELOP по SCP/SFTP; `docker compose up -d --build`
пересобирает только эту копию. Git push не выполняет выкладку автоматически.

Браузерная форма доступна через SSH-туннель только к `127.0.0.1:18080`:

```sh
ssh -i "ключ" -N -L 127.0.0.1:18080:127.0.0.1:18080 botai-dev@135.106.182.11
```

Затем открыть `http://127.0.0.1:18080/ui/`.
SSH запрещает remote, agent, X11 и Unix-socket forwarding; PermitOpen разрешает
только develop-порт. Основной API не проксирует develop-код: общий browser origin
позволил бы изменённой странице обращаться к основному сервису от имени пользователя.
Владелец добавляет DNS `develop.botai-ege.ru`. Отдельный Caddy vhost подготовлен:
своя Basic-авторизация; удаление Cookie и Authorization перед upstream, Set-Cookie,
Location и CORS-заголовков из ответов; только UI и photo-check/config. Внешняя
проверка HTTPS на момент завершения настройки 1 октября ожидала DNS и сертификат.
До подтверждения внешнего HTTPS использовать туннель.
Публичная инструкция содержит только placeholders «ключ»,
«пользователь», «адрес», без реальных реквизитов и внутренних путей.

## Граница ключа

Настоящий ключ провайдера не копируется в DEVELOP. Его единственная новая копия —
`/srv/gateway/secrets.json` (root:root 600). systemd передаёт её шлюзу через
`LoadCredential`; ключ отсутствует в аргументах процесса и переменных окружения.
Разработчик не читает каталог шлюза, systemd credentials или окружение его процесса.

`.env` DEVELOP содержит отдельный отзываемый токен шлюза. Сам разработчик может
читать этот токен и менять окружение своей копии. Это не ключ DeepSeek.
Шлюз слушает только `127.0.0.1:8091`, а контейнер обращается к нему через rootless
host alias `10.0.2.2:8091/v1`.

Разрешён только `POST /v1/chat/completions`, модель `deepseek-v4-flash`, фиксированный
HTTPS upstream `api.deepseek.com`. Нет произвольного URL, redirects, streaming
или выполнения tools на шлюзе. Authorization клиента не передаётся провайдеру.
Ошибки upstream не выдаются наружу; секреты дополнительно удаляются из декодированных
JSON-ключей и значений успешного ответа. Тела запросов, изображения и ключи не логируются.

По решению владельца **нет квоты числа вызовов и суммарного бюджета**.
Технические ограничения: 4 одновременных upstream-вызова, 24 принятых соединения,
20 секунд чтения входного соединения, 360 секунд upstream, 48 МиБ тело запроса,
8 МиБ ответ. Занятый шлюз возвращает 429. Допустимые запросы расходуют баланс владельца.

## Ограничения сервера

- UID 1000 и subordinate UID 100000–165535 закрыты от локальных административных
  сервисов, production-портов, частных сетей, metadata, собственного публичного IP
  и IPv6. Разрешены шлюз, собственный develop-порт и локальный DNS.
- Rootless slirp host-loopback включён для шлюза; граница доступа — firewall хоста,
  а не настройки, которые разработчик может изменить в своём Docker.
- Firewall применяется атомарным `iptables-restore --noflush`.
  systemd user manager требует firewall; SSH shell дополнительно проверяет его
  через адресный PAM hook. Root/admin SSH этим hook не ограничивается.
- `/srv/ege` закрыт от пользователя на уровне родительского каталога; внутренняя
  структура и права `app/` не изменены. Закрыты резервные Caddyfile в `/etc`, `/opt`
  и найденные временные копии. `/srv/auth` и root Docker остаются недоступны.
- Дом, проект, Docker и временные файлы разработчика размещены на томе 8 ГБ.
  SSH получает private `/tmp` и `/var/tmp` через PAM; user manager — через BindPaths.
- На пользовательскую slice: MemoryMax=1500M, MemoryHigh=1200M, CPUQuota=100%,
  TasksMax=512, swap отключён. Контейнер имеет отдельные меньшие лимиты.
- Journald ограничен 256 МиБ на диске и 64 МиБ в runtime; отключено дублирование
  в syslog. Fail2ban уже использовал journald backend и продолжает работать.
- Caddy отклоняет чужой Origin для основного API/auth/internal/debug и frontend API;
  разрешены production origins api/www/apex. Запросы без Origin сохраняют прежнюю
  авторизацию. Прямые вызовы из localhost-фронтенда к production grading теперь
  должны идти через доверенный путь или отдельный DEVELOP.

Это изоляция пользователей и контейнеров на общем kernel, не отдельная VM.
Проверки не являются гарантией отсутствия неизвестных уязвимостей.

## Снимки и проверка

Исходный приватный снимок: `/root/backups/botai-security-before-develop-20261001`.
Содержит архив конфигурации SSH/UFW/Fail2ban/Caddy/Docker, первоначальные firewall
rules, effective SSH config, inspect основного контейнера и SHA256/permission
манифесты `/srv/ege/app`. Архив содержит секреты; его нельзя передавать разработчику
или помещать в Git. Итоговое состояние хранится рядом в `after/`.

Проведены пять независимых раундов security review с исправлениями. Проверены
реальный SSH-вход временным ключом, разрешённый tunnel к DEVELOP, запрещённый tunnel
к Caddy admin, shell/container file/network boundaries, Origin и публичные пути.
27 gateway security tests и полная офлайн-suite: 392 passed, 3 skipped.
Полный конвейер копии выполнен в отдельном контейнере с `--network none` и mock.
Шлюз проверен с неверным токеном/моделью без upstream-вызова. Платный end-to-end
вызов модели при этой настройке не выполнялся.

У отдельного sibling-поддомена остаётся браузерный риск cookie tossing: JavaScript
может задавать Domain-cookie для родительского домена. Host-only сессионные cookies,
CSRF, смена session ID при входе и запрет чужого Origin снижают риск захвата сессии,
но для полного устранения этого класса конфликтов нужен отдельный регистрируемый
домен. SSH localhost остаётся альтернативой. Это не даёт доступа к ключу провайдера.

### Побочное действие установки

При установке rootless extras пакетный менеджер подтянул Docker 29.8.2 вместо
29.8.0 и перезапустил системные контейнеры. Все три Docker-пакета возвращены на
29.8.0; основной сервис восстановился. Файлы, права, ID, образ, Config и mounts
основного контейнера сохранены; время старта изменилось. В HostConfig Docker
нормализовал пустые Dns/DnsSearch/DnsOptions из null в пустые списки; смысл
настройки не изменился. Владельцу сообщили об
этом во время работы. В дальнейшем устанавливать пакеты с явной версией и
проверять план apt до применения; не считать сохранение файлов отсутствием перезапуска.

## Обслуживание и откат

Администратор управляет `botai-gateway.service` и `botai-develop-firewall.service`.
Для отзыва доступа сначала убрать публичный SSH-ключ, завершить сеансы пользователя,
остановить его контейнеры/user manager и сменить токен шлюза. Один отзыв SSH-ключа
не прекращает уже открытые сеансы.

Для полного удаления сначала закрыть доступ и остановить DEVELOP/gateway, затем
убрать адресные PAM/SSH/systemd/fstab additions и Caddy-инструкцию/Origin policy
по сохранённому diff. Отключать firewall следует только после остановки всех
процессов пользователя и удаления его доступа. Нельзя слепо восстанавливать старый
iptables-save или весь Caddyfile поверх последующих изменений. Основной `.env`
не требует восстановления, поскольку не менялся. Снимки с секретами сохранять root-only.

## Инцидент ожидания модели — 1 октября, после 22:28 МСК

После увеличения лимита DEVELOP-запрос `req_5a563bdca3554d4f`, начатый около
23:26:15 МСК, завершился 504 через 480 секунд. На шлюзе оставался один worker:
соединение клиента находилось в CLOSE-WAIT, соединение с upstream — ESTABLISHED.
Это подтверждает оставшийся upstream-запрос после отключения клиента, но не
блокировку всех запросов: шлюз имеет четыре независимых слота.

Повторный перезапуск шлюза в 23:39 МСК убрал зависшее соединение. Затем владелец
явно разрешил два коротких платных теста: напрямую и через шлюз, с одинаковыми
моделью и сообщением. Прямой вызов получил HTTP 200 headers за 0,38 секунды,
но не завершённый JSON; оба тестовых клиента завершились по таймауту примерно
через 35 секунд. Следовательно, задержка воспроизводится без шлюза. Это не
доказывает глобальный сбой DeepSeek или конкретную причину внутри провайдера.

У прежнего `HTTPSConnection(timeout=480)` был таймаут отдельных операций сокета,
а не абсолютный предел запроса. Периодические данные могли продлевать ожидание.
DeepSeek документирует пустые строки keep-alive во время ожидания inference:
https://api-docs.deepseek.com/quick_start/rate_limit/ . В этих тестах содержимое
незавершённого ответа не сохранялось, поэтому получение именно таких строк
не утверждается как непосредственно измеренный факт.

Исправление установлено только в `/srv/gateway/gateway.py`: watchdog прерывает
сохранённый upstream-сокет по общему бюджету 480 секунд, включая потраченное время
подключения. Подключение имеет отдельный socket timeout 30 секунд. DNS выполняется
системным resolver до установки watchdog и не имеет этой же строгой гарантии;
его прошедшее время учитывается при возвращении управления. Отключение клиента
не отменяет upstream немедленно, но дальнейшее ожидание ограничено этим бюджетом.
Шлюз возвращает 504 `upstream_timeout`, освобождает слот и записывает только
случайный request ID, этап, длительность и upstream HTTP status. Тела, ключи,
заголовки и текст исключений не логируются.

31 офлайн gateway-тест прошёл: в том числе реальные локальные сокеты с медленными
заголовками, бесконечными chunked/close-delimited данными, освобождение слотов и
обычный успешный ответ. Новое независимое security review одобрило узкую выкладку.
После перезапуска: health 200, неподдерживаемая модель с валидной авторизацией 400
без обращения к провайдеру, `/v1/models` 404 по контракту. Успешная inference после
исправления не подтверждена; изменение устраняет зависшие соединения, а не
доказанную первопричину задержки upstream. Приватная копия прежнего кода и манифест
основного app сохранены в `/root/backups/botai-gateway-hang-20261001`.
