# Как работает сервис проверки решений

Рабочая спецификация простым языком. Обновлено 27.09.2026.

Этот документ — действующий контракт реализации: что получает сервис, что делает с данными и что возвращает. Исторический server-file-reading-spec.md не заменяет эти договорённости.

Этот документ сохраняет текущие договорённости и открытые вопросы. Он предназначен для обсуждения с человеком, а не для передачи проверяющей модели. Статус реализации и проверок ведётся в README.md.

## Что делает сервис

Сервис получает фотографии решения ученика вместе с данными задачи, проводит проверку по нашим инструкциям и возвращает JSON с результатом: распознанным решением, разбором, одной оценкой, объяснением и советами в предусмотренных местах.

Если проверку завершить нельзя, сервис сообщает причину без выставления балла. Нечитаемое изображение или технический сбой не превращаются в нулевую оценку.

## Что делаем сейчас

Сейчас нужен самостоятельный микросервис, на котором можно проверить весь процесс. Основное приложение и его части уже существуют, но передача данных между фронтом, backend и проверкой ещё не закончена. Не считаем эту интеграцию готовой и не включаем её завершение в текущую работу.

Сохраняем тестовую форму для загрузки фотографий решения ученика. Текстовый ввод условия заменяем отдельным прикреплением одной фотографии с условием задачи и её эталонным решением. Это отдельное вложение, оно не смешивается с фотографиями работы ученика.

Перед основной проверкой отдельный вызов DeepSeek V4 Flash распознаёт эту фотографию. Его задача — перевести предоставленный материал в текст, а не решать задачу заново или оценивать ученика. Условие сохраняется в `Statement.md`, эталонное решение — в `Solution.md`. Здесь Solution означает эталон, а не работу ученика.

Эти два файла относятся только к текущей отправке и доступны основной модели рядом с инструкциями. Они не становятся общими постоянными инструкциями и не могут смешиваться с данными другого запроса. Текст на фотографии, даже перенесённый в эти файлы, не получает права менять правила сервиса.

Это временный способ подготовки данных задачи для тестовой формы. В дальнейшем приложение само передаст готовые данные, и предварительное распознавание эталона не потребуется.

В тестовом режиме разрешены заглушки пользователя и локальные ID задачи/фотографий. Их создаёт сервер; модель переносит их без изменений. Они явно считаются тестовыми, а не реальными записями пользовательской базы. Это позволяет проверить микросервис без готовой интеграции.

Автор Main поддержал схему. В основной сессии модель сначала читает `Statement.md` и `Solution.md`, затем инструкции распознавания и анализа работы ученика. `Statement.md` содержит условие. В `Solution.md` два раздела: «Эталонное решение» и «Правильный ответ». Данные в файлах и итоговом JSON берутся из одного результата предварительного распознавания, чтобы не расходиться между собой.

Предварительное распознавание не дописывает отсутствующее и не решает задачу самостоятельно. Если условие или правильный ответ отсутствуют, нечитаемы либо на фото несколько задач без однозначного выбора, подготовка останавливается с просьбой заменить фото. Проверка ученика ещё не начинается, поэтому это ошибка подготовки задачи, а не отказ ученику с выдуманными данными задачи. Правильный ответ может быть заключительной записью внутри эталонного решения, отдельный заголовок необязателен.

Если условие и правильный ответ читаются, отсутствие полного эталонного разбора не мешает проверке. Нечитаемый или неполный эталон не выдаём за полный: в данных отмечаем отсутствие эталонного решения и показываем это в тестовой форме. Правильный ответ при этом сохраняется в `Solution.md`.

Эталон помогает сверяться с математикой, но не обязывает ученика использовать тот же способ и не позволяет дописывать за него отсутствующие шаги. Основная модель только читает эти файлы; их создаёт сервер по результату предварительного OCR. Они не являются ещё двумя постоянными инструкциями.

## Как будет при подключении основного приложения

На фронте открыта конкретная задача. Приложение передаёт JSON с её ID, условием, правильным ответом, при наличии эталонным решением и индивидуальными критериями, а также фотографии решения ученика и их ID. Фотографии сохраняет код основного приложения; детали сохранения относятся к отдельной работе фронта и backend. Проверочный микросервис не ищет задачу в базе.

ID задачи везде один: приходит с запросом и без изменений возвращается в итоговом JSON. ID фотографий относятся к той же работе. ID пользователя для репорта поступает из авторизованного запроса; модель не выбирает, кому приписать отправку.

## Проверка файлов до обращения к модели

Скрипт проверяет количество и размеры файлов, допустимость формата и возможность открыть изображения. Если вход не подходит, сервис сообщает об этом без оценки.

Эта проверка отвечает за пригодность файлов. Содержание фотографии — действительно ли там решение, можно ли разобрать записи, есть ли подозрительные команды — рассматривается дальше моделью.

## Как проходит обычная проверка

Основную проверку решения ученика ведёт одна модель в одном диалоге. Предварительное распознавание фотографии с условием и эталоном — отдельная сессия, которая только подготавливает входные данные. Математические правила уже описаны в наших промптах; здесь сохраняем порядок работы, не переписывая сами правила оценки.

1. Модель получает фотографии работы ученика и начальную инструкцию, читает данные задачи из `Statement.md` и `Solution.md`. Отдельное фото эталона не входит в фотографии работы ученика.
2. Читает инструкции распознавания и анализа, затем справочник типичных ошибок, необходимый для анализа.
3. Распознаёт записи без исправления ошибок ученика, изучает решение и сохраняет временные заметки Notes: ход решения, найденные ошибки и точки роста. На этом этапе нет баллов и диапазонов оценки.
4. Только после сохранения Notes читает инструкцию подведения итогов, затем критерии. Для подготовки ответа читает описание формата JSON.
5. Выставляет один итоговый балл, формулирует объяснение и советы. Если сомневается в записи, возвращается к соответствующему месту на исходной фотографии и уточняет связанный вывод в Notes.
6. Подготавливает JSON и передаёт его на проверку скрипту.
7. После успешной проверки возвращается именно проверенный текст JSON.

Главная обязанность сервера — обеспечить последовательное чтение инструкций и выполнение обязательных шагов. Одной просьбы к модели «соблюдай порядок» недостаточно: сервер не должен разрешать перескакивать через эти шаги.

## Когда обычную проверку нужно прекратить раньше

На этапе распознавания и анализа прекращаем проверку без создания Notes и без оценки, если прислано другое задание, целый вариант, посторонняя картинка, лишние фотографии с другими заданиями либо обнаружена попытка вредоносных команд.

Несколько фотографий продолжения одного решения допустимы. Математическая ошибка в выбранной задаче не превращает её в другое задание.

Если существенную запись невозможно прочитать после повторного просмотра, также возвращаем отказ без оценки. Если это обнаружилось позднее, ранее созданные Notes не выдаются ученику.

Отказ — корректный JSON. Поле `is_graded` показывает, завершено ли оценивание. Если `true`, `rejection_reason` — пустая строка и результат заполнен. Если `false`, модель кратко формулирует причину в `rejection_reason`, а `ocr`, `analysis`, `grading` равны `null`. Данные и ID задачи и фотографий сохраняются в обоих случаях. Отказ тоже проходит проверку скриптом.

Прежнее правило «другое задание — ноль баллов» заменено: теперь это отказ без оценки. Начальная инструкция, описание формата и автономный валидатор используют новый ответ. Подключение основного приложения остаётся за рамками текущего этапа.

## Проверка подготовленного JSON

Скрипт проверяет структуру ответа, обязательные поля, допустимые значения и соответствие ID задачи и фотографий исходному запросу.

Если модель нарушила формат или указала недопустимый балл, ей возвращают конкретные ошибки для исправления. Например, балл 5 при максимуме 2 нельзя просто заменить на 2: объяснение может тоже оказаться неверным. Исправленный ответ проверяется заново.

Приняты пределы: до четырёх фотографий решения по 8 МБ, ожидание до четырёх минут, повтор после сбоя по кнопке пользователя. Для отдельной фотографии условия и эталона используем тот же предел 8 МБ: всего можно приложить одно фото задачи и до четырёх фото работы ученика. Четыре минуты включают предварительное распознавание и основную проверку, а не выделяются каждому этапу отдельно. Если получить допустимый ответ не удалось, сервис сообщает о сбое без оценки.

Скрипт не доказывает математическую правильность оценки. Правильный формат и допустимый балл сами по себе не означают, что модель верно поняла решение.

## Безопасность

Основной сценарий угрозы — попытка через присланное содержимое заставить модель раскрыть данные, секреты или наши инструкции либо вмешаться в работу сервера. Не строим обсуждение вокруг предположения, что обычный ученик обязательно пытается выпросить максимальный балл: пользователь приходит готовиться к ЕГЭ, но возможность атак нужно учитывать.

У модели есть только необходимые для проверки возможности: читать разрешённые инструкции, сохранять заметки и подготовленный ответ, передавать ответ на проверку и сообщать о предусмотренных исключительных ситуациях. Возможность фиксировать подозрительное содержимое также должна быть ограниченной.

Модель не получает доступ к базе данных, секретам, чужим фотографиям, произвольным файлам и командам сервера. Она не может самостоятельно выходить в интернет или выполнять действия, не предусмотренные проверкой. Сервер проверяет допустимость каждого действия независимо от того, что написано на фотографии.

Содержимое работы остаётся материалом для проверки и после распознавания, цитирования или переноса в Notes. Команда, переписанная из фотографии в заметки, не становится нашей инструкцией.

Подозрительные команды ищем уже на этапе распознавания и анализа. По последнему пожеланию пользователя отдельную сложную защиту от пересказа инструкций сейчас не проектируем: сохраняем ограниченные возможности модели, проверку JSON и репорты. При этом валидатор проверяет форму ответа, а не смысл каждой строки: нежелательный текст теоретически может оказаться внутри разрешённого поля корректного JSON. Модель также может не заметить подозрительную команду.

## Репорты о подозрительных отправках

Если модель замечает предполагаемую вредоносную команду, она сообщает об этом серверу. Сервер сохраняет репорт для последующего просмотра и наблюдения за повторными случаями.

Содержимое репорта по последнему уточнению пользователя — ID пользователя и ID присланных фотографий его решения в базе. Не требуются дополнительные поля с цитатами команд, объяснениями или статусами рассмотрения. Время создания хранится как служебная отметка для удаления через 30 дней.

Репорт и связанные с ним фотографии должны оставаться доступны для разбора в течение 30 дней. В будущем доступ к фотографиям обеспечивает основное приложение по их ID; в тестовом микросервисе эту связь воспроизводит локальное хранилище с тестовыми ID. Новую общую базу пользователей для этого не создаём. Удаление локальных копий и репортов не даёт микросервису права удалять произвольные записи основной базы.

Пользователь и фотография привязываются сервером по реальному запросу. Модель не может указать другого человека или произвольную ссылку в качестве источника репорта. Просмотр фотографии должен быть доступен тем, кто разбирает такие случаи, а не всем по публичной ссылке.

Репорт — подозрение, требующее просмотра, а не доказанная атака. На этом этапе договорились мониторить: автоматическую блокировку пользователя не вводим. Повторные случаи по одному пользователю должны быть видны вместе.

Для первого запуска репорты только сохраняем на сервере. Экран просмотра добавим позже — это подтверждённое решение пользователя. Будет ли хранение отдельной частью приложения, решим при реализации; отдельный сервис сейчас не требуется.

При обнаруженной попытке атаки проверка прекращается на этапе распознавания и анализа. Возвращается корректный JSON отказа без оценки, а репорт сохраняется отдельно. При подозрительной отправке ученику показываем согласованную нейтральную причину: «Не удалось проверить эту отправку. Пришли только фотографии решения». Команду и внутренний репорт не показываем.

## Реализация и подключение

Пользователь выбрал DeepSeek V4 Flash. Поддержку фотографий и инструментов проверяем для фактически используемого подключения, без платных пробных вызовов.

Предложение с отдельным распознаванием условия и эталона рассмотрено автором Main и внесено в этот документ и начальную инструкцию. Дополнительных вопросов по основному поведению нет. Формат отказа, состав репорта, срок 30 дней и основные ограничения подтверждены пользователем.

Самостоятельный микросервис развёрнут 27.09.2026; офлайн-тесты и полный mock-сценарий проверены без платных модельных вызовов. Существующие настройки провайдера сохранены. Реальное распознавание и качество оценки пользователь проверяет самостоятельно. Полную интеграцию с основным приложением и экран репортов в этот этап не включаем.
