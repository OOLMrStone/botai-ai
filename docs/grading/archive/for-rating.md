# Пожелания к будущему grading.md

Для следующего редактора промпта, не для проверяющей модели. Это запись договорённостей пользователя, а не готовый `grading.md` и не восьмой файл серверного пакета.

## Задача этапа

- Прочитать временный `Notes.md`, подготовленный по `analysis.md`, и оценить работу целиком по `criteria.md` с учётом `popular_mistakes.md`. Выдать один балл: 0, 1 или 2, объяснение и полезные советы.
- В спорном случае снова обратиться к распознаванию, собственному анализу и точному правилу справочника. Проверить и возможную излишнюю строгость, и необоснованное смягчение. Не повторять всю процедуру без необходимости; итог должен учитывать разрешённое сомнение.
- JSON нужен для фронта и простого просмотра качества: сопоставить фото с OCR и понять, обоснован ли ответ модели. Технический журнал запусков, версии отчётов, статусы валидации и рецензии экспертов в него не входят.
- Данные задачи и ID фотографий поступают из базы/запроса. Сохранить условие, правильный ответ и переданное правильное решение для показа на фронте. Не придумывать ID и отсутствующее эталонное решение.

## Как заполнять текст

- `ocr` — одна строка с переносами: сначала записанная ОДЗ, затем ход решения в логическом порядке. Можно переставить блоки и добавить заголовки; нельзя исправлять ошибки или дописывать недостающую математику. Значимые оси и неясные места описываются в этом же тексте. Построчных ID и ссылок на них нет.
- `analysis.summary` — связный разбор этапов: что сделано верно, где ошибка и как она повлияла на дальнейшую работу. Здесь можно раскрыть причины и последствия; не превращать каждое следствие одной ошибки в отдельную независимую ошибку.
- Проверки имеют понятные bool: `is_correct`, `is_complete`. Неприменимость не означает ошибку, а неизвестность не кодируется как `false`. Формат ещё не определяет отдельный ответ для неустранённой существенной неясности.
- `strengths` — конкретные подтверждённые удачные действия. Не требовать похвалу ради заполнения списка.
- `grading.explanation` — понятное ученику объяснение балла по этой работе; `criterion` — применённый критерий. Не дублировать это отдельными `evidence`, `rechecks`, `feedback` и журналами правил.

## Одна ошибка — одна карточка

Порядок полей: `id`, `code`, `description`, `where`, `correct_version`, `advice`.

| Поле | Пожелание пользователя |
| --- | --- |
| `id` | Идентификатор конкретной ошибки в работе; это не код из справочника |
| `code` | Подходящий E-код; если ошибки нет в справочнике — `null`, без выдуманного кода |
| `description` | Короткое общее название ошибки, как в таблице: например, «Исключена допустимая граничная точка». Не добавлять сюда числа этой работы, последствия и пояснение балла |
| `where` | Полная узнаваемая ошибочная строка или несколько связанных строк из работы, чтобы легко найти место. Не ограничиваться вырванным символом или коротким ответом без контекста, если этого недостаточно. Не подменять цитату словами «в конце решения» |
| `correct_version` | Тот же фрагмент и тот же объём контекста, но с исправленной ошибкой. Именно исправленная запись, а не объясняющий абзац |
| `advice` | Готовый полезный совет строкой прямо внутри ошибки; отдельного списка советов и `error_ids` нет |

Для отсутствующего шага не выдумывать ученическую цитату: привести ближайшую действительную запись и отдельно обозначить пропуск. В `correct_version` показать недостающий переход. Советы брать из Notes и колонки справочника, адаптируя к работе; указания «Для модели: …» выполнить, а не копировать ученику.

## Особые случаи и оставшийся вопрос

- По последнему решению пользователя другое задание — ранний отказ без Notes и оценки: `is_graded=false`, краткая непустая `rejection_reason`, `ocr/analysis/grading=null`. Так же обрабатываются целый вариант, посторонняя картинка и лишние фото других заданий. При завершённой проверке `is_graded=true`, причина строго пустая. Поле `is_target_task` удалено. Обычная ошибка преобразования выбранной задачи не является другим заданием.
- При верной работе не придумывать ошибку ради совета. Пользователь ранее разрешил точки роста и советы без ошибок; после переноса совета внутрь ошибки место таких советов в JSON ещё нужно согласовать. Это открытый вопрос, а не отмена требования.
- Валидация — внешний скрипт проверки полей, типов и согласованности. Невалидный формат возвращается модели на исправление; сведения о проверке не включаются в ответ. Технический сбой не является нулевой оценкой ученику.

Структура и типы — в [response-format.md](../../../tasks/common/prompts/response-format.md). Пустой [шаблон JSON](response-template.json) показывает форму: `""`, `0` и `false` — заполнители, не результат проверки. По одному элементу массива оставлено для демонстрации его структуры; в реальном ответе пустые списки допустимы. Разрешённые случаи `null` описаны в формате.

При дальнейшем обсуждении пользователь просит всегда показывать JSON в конце ответа. Сейчас согласуется структура; этот файл помогает затем написать промпт, не смешивая задачи.
