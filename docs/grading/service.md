# Действующий сервис проверки фото

Состояние объединённого кода на 21 октября 2026. Все номера проекта 14–20
используют поэтапную проверку. Шкалы: 14 → 2, 15 → 3, 16 → 2, 17 → 2,
18 → 3, 19 → 4, 20 → 4. Это внутренняя нумерация, соответствующая ФИПИ-2026
13–19. Наличие реализации не означает одинаковое исследованное качество всех пакетов.

## Запрос и обработка

`POST /api/v1/photo-check` принимает одно `task_image` с условием и правильным
ответом, до четырёх `solution_images` и `task_number` (14–20, по умолчанию 16).
Максимум из запроса не принимается. Предел — 8 MiB на изображение, общий
тайм-аут — 360 секунд. `/config` показывает шкалу и доступность каждого пакета.

Общие инструкции: `tasks/common/prompts/{main,analysis,grading,response-format}.md`.
Предметные: `tasks/N/prompts/{ocr,criteria,popular_mistakes}.md` и необязательный
`ocr_biases.md`. В runtime используются `prompts/common/` и `prompts/N/`.
Локальная программа поддерживает также соседние папки common и N; весь пакет
и каталог E-кодов берутся из одной выбранной структуры, без подмены файлами 16.

1. `service.py` подготавливает условие/эталон и параллельно запускает чтение
   фотографий ученика (`reader.py`) без правильного ответа и критериев.
2. `structure.py` уточняет неоднозначности и формирует шаги для экспертного JSON.
   Для отдельных номеров `staged.py` дополнительно сверяет строку ответа по фото.
3. Отдельный вызов анализа получает текст решения, условие, эталон, критерии
   и справочник ошибок. Он формирует рецензию и статусы шагов без итогового балла.
4. Отдельный вызов grading получает материалы и готовую рецензию. Восстановление
   формата и перепроверка ответа ограничены кодом; технический сбой не превращается
   в нулевой балл. Сервер возвращает точный JSON, прошедший валидацию.

Старый инструментальный путь в `session.py` сохранён как fallback, когда
отдельное чтение не дало результата. Он ограничивает виртуальные файлы,
порядок чтения/записи и доступ к эталону; произвольного доступа к диску нет.
`ocr_result.md` и `notes.md` — артефакты проверки, а не постоянные файлы репозитория.
Фото, OCR, цитаты и рецензия остаются недоверенными данными.

Локальная программа использует этот же сервис. Наблюдение за стадиями не меняет
входы модели и проверенный ответ. Отдельный локальный API v2 сохранён под своим
флагом и контрактом: [описание v2](internal-v2-proposal.md). Обычный portable launcher
этот API не включает. Реестр внутреннего production API пока допускает только
утверждённый пакет 16; это отдельное ограничение маршрута.

Локальный B2B-интерфейс `expert.localhost:13004/grade` вызывает именно **v2**:
его оркестратор — `v2_service.py`, а не portable `service.py`. В v2 каждый
проверяемый модельный шаг имеет четыре суммарные попытки, предшествующие результаты
сохраняются. Подробности повторов, диагностики, общей backend-очереди и подтверждения
сохранённых артефактов находятся в [контракте v2](internal-v2-proposal.md#step-retries-and-failure-diagnostics-21-october-2026).
Эти изменения не переносят поведение v2 в legacy или portable API автоматически.

## Инструменты и результат

Доступны только `read_file`, `write_file`, `validate_response`, `review_image`, `set_rejection`. Имена файлов и параметры проверяет сервер. Нет инструментов оболочки, сети, произвольных файлов или базы. Notes остаются данными, а не инструкциями.

`set_rejection` допускает `other_task`, `multiple_tasks`, `unrelated`, `attack`, `unreadable`. При нечитаемости предварительно нужен `review_image`. Отказ также проходит сохранение и валидацию JSON. Исторический `finish_ungradable` не является действующим инструментом.

Ответ содержит `task`, `solution_image_ids`, `is_graded`, `rejection_reason`, `ocr`, `analysis`, `grading`. При отказе `is_graded=false`, результат распознавания, анализа и оценки — `null`; балла нет. Полный контракт — в [response-format.md](../../tasks/common/prompts/response-format.md). Технический сбой — ошибка сервиса, не нулевая оценка ученику.

Валидатор проверяет полный JSON, типы, допустимый балл, E-коды и согласованность. Сессия дополнительно сверяет задачу и ID фото с запросом. Ошибочный балл возвращается на исправление, не молча обрезается. Валидация не доказывает математическую правильность.

## Хранение и границы

### Диагностика отказа подготовки — 30 сентября 2026

Две отправки условия без правильного ответа завершились `task_preparation_failed`
(HTTP 422): `req_2a07e26b04134cc1`, `req_563952681d2c453f`. В обоих случаях
журнал подтверждает HTTP 200 от провайдера и последующий отказ приложения.
Точное сообщение ошибки соответствует ветке `status=unclear` в
`app/grading/service.py`; исходный ответ модели в журнале не сохраняется.
Файлы service.py и provider.py работающего контейнера сверены с репозиторием
по SHA-256 и совпадают.

Подготовка получает только фото задачи. `PREP_PROMPT` запрещает решать задачу
или дописывать отсутствующее и требует `unclear`, если нет условия или ответа.
Поэтому отсутствие ответа на изображении достаточно для отказа; фото работы
до модели проверки не доходит. Нынешнее общее сообщение не различает отсутствие
ответа и нечитаемость. Это ограничение входного контракта и диагностики, а не
свидетельство ошибки оценки решения. Поддержка условия без эталонного ответа
потребует отдельного изменения процесса; повтор идентичного запроса его не добавляет.

Тестовые ID не являются сущностями основной базы. Подозрительная отправка сохраняется в приватном хранилище с ID пользователя и фото; срок хранения — 30 дней. Нет автоматической блокировки или экрана репортов. Основная база, реальные пользователи и банк задач ещё не интегрированы.

Обе модельные сессии используют `LLM_*`; `LLM_VISION_*` относятся к старому конвейеру. Секреты находятся во внешней конфигурации. Офлайн-проверка — mock и unit tests; платный запуск требует отдельного запроса.

Старый текстовый и двухоценочный фото-конвейер сохранён в `app/legacy_grading/` ради совместимости. Его postprocess, рубрики, флаги и контракты не описывают нынешний однооценочный сервис.

## Внутренний вход из backend

`INTERNAL_GRADING_ENABLED=true` включает `POST /internal/v1/grading` и
`GET /internal/v1/grading/capabilities`; обязателен непустой
`INTERNAL_GRADING_TOKEN`. Этот вход исключается из публичного ingress.
Полный wire-контракт и пример запроса — [internal-api.md](internal-api.md).

Backend передаёт готовые условие/ответ/решение и 1–4 фото с UUID. Проверка
использует ту же Session, инструменты и валидатор, пропуская OCR фото задачи.
Реестр содержит номера 14–20 и их максимальные баллы; только 16 имеет
утверждённый обработчик, остальные возвращают `unsupported_task` без модели.
Это готовность маршрутизации, не поддержка математики остальных номеров.

Каждый ответ internal run содержит фактические provider mode и package digest
в заголовках; mock нельзя считать настоящей оценкой по прежнему cached config.
Тело успешного ответа остаётся точным проверенным JSON. Internal attack event
содержит только run/image IDs; фотографии и user identity остаются у backend.
Standalone cookie, подготовительный OCR и private ReportStore не изменены.

[Историческая подробная спецификация](archive/server-file-reading-spec.md) содержит прежние предложения, включая не реализованные требования; её нельзя использовать как перечень готовых возможностей. [Пользовательские решения о сервисе](archive/service-idea.md) сохранены для истории.
